# 검색 기능 확정 정의서 (spec-fixed)

> 원본: `spec-original.md` — "본문 내용을 search 하는 기능을 개발하고 싶어"
> 상태: **사용자 확정 대기 중**

## 1. 개요

사이드바의 노트 목록을 검색어로 걸러 보는 기능. 검색은 **보기 필터**일 뿐이며 노트 데이터와 편집 상태를 바꾸지 않는다.

## 2. 확정된 결정 사항

| #   | 주제                  | 결정                                                                                                     | 이유                                                                          |
| --- | --------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 1   | 검색 범위             | `title` + `content` 모두 검색                                                                            | 사용자는 제목/본문을 구분해 기대하지 않음                                     |
| 2   | 검색 방식             | 클라이언트 필터링 (`notes`를 `includes`로 거름). 서버 `?q=` 미사용                                       | 이미 전체 `notes`를 로드한 상태이고, 네트워크/debounce/레이스 컨디션이 불필요 |
| 3   | 결과 표시             | 하이라이트·스니펫 없음. `NoteItem` 표시는 그대로                                                         | 첫 버전은 필터링에 집중, 표시 계층은 나중에 분리해 추가 가능                  |
| 4   | 매칭 규칙             | 대소문자 무시, 앞뒤 공백 trim, 구문 일치(`includes`). 공백만 입력하면 검색 안 한 것으로 취급             | 가장 단순하고 가장 흔한 불편(대소문자)을 해소                                 |
| 5   | UI 위치/상태          | 사이드바 상단 `NoteSearch` 입력창. `query` state는 `App.tsx`에 lift-up, `NoteList`가 props로 받아 필터링 | 기존 "UI 상태는 App, 서버 데이터는 Context" 규칙 준수                         |
| 6-1 | 결과 0건              | "검색 결과가 없습니다" (노트 자체가 없을 때의 "노트가 없습니다"와 구분)                                  | 사용자가 다음 행동을 판단할 수 있음                                           |
| 6-2 | 선택 노트가 걸러질 때 | `selectedNoteId` 유지, 에디터 그대로                                                                     | 작성 중 입력 손실 방지                                                        |
| 7-1 | 검색어 지우기         | 입력이 있을 때만 ✕ 버튼 표시. 클릭 시 `query` 비우고 입력창에 포커스 복귀, `aria-label="검색어 지우기"`  | 좁은 사이드바에서 일반적인 패턴                                               |
| 7-2 | 개수 표시             | 검색 중 "검색 결과 N개", 평소 "노트 N개"                                                                 | 현재 상태를 구분해 표시                                                       |
| 8   | 검색 중 생성/수정     | 필터 규칙을 그대로 적용 (일치하지 않으면 목록에 안 보임). 에디터는 유지됨                                | "검색은 보기 필터" 원칙과 일관, 예외 규칙 없음                                |

## 3. 가정 (인터뷰에서 따로 묻지 않음 — 확인 필요)

- **debounce 없음**: 클라이언트 동기 필터링이므로 입력할 때마다 즉시 필터링한다.
- **접근성**: 입력창에 `label`(시각적으로 숨겨도 됨) 연결, `type="search"` 사용, ✕ 버튼은 키보드 접근 가능한 `button`.
- **반응형**: 검색창은 사이드바 너비(`w-72`)를 따른다. 사이드바 자체의 반응형 개선은 이번 범위가 아니다.
- **검색어 영속화 없음**: 새로고침하면 검색어는 초기화된다. URL 쿼리에 반영하지 않는다.
- **정렬**: 기존 목록 순서를 유지한 채 걸러내기만 한다 (관련도 정렬 없음).
- **삭제**: 검색 중 노트를 삭제하면 기존대로 `removeNote`가 동작하고, 남은 결과로 목록이 갱신된다.

## 4. 시나리오 (최소 동작)

1. 사용자가 검색창에 `react`를 입력하면, 제목 또는 본문에 `react`(대소문자 무관)가 포함된 노트만 목록에 남고 상단에 "검색 결과 N개"가 보인다.
2. 일치하는 노트가 없으면 "검색 결과가 없습니다"가 보인다.
3. ✕ 버튼을 누르면 검색어가 지워지고 전체 목록과 "노트 N개"가 돌아오며 입력창에 포커스가 간다.

## 5. 경계 조건

- 빈 문자열/공백만 입력 → 전체 목록 (필터링 안 함)
- `title`이 빈 노트, `content`가 빈 노트도 나머지 필드로 검색 가능
- 로딩/에러 상태가 우선: 기존 `loading` → `error` → 빈 목록 → 정상 렌더 순서의 early return 유지. 검색 입력창은 이 상태와 무관하게 사이드바 상단에 항상 표시된다 (`NoteList` 바깥에 위치).
- 노트가 0건일 때는 "노트가 없습니다"가 우선하고, "검색 결과가 없습니다"는 노트가 1건 이상 있을 때만 쓴다.

## 6. 용어 정의 (Ubiquitous Language)

| 용어            | 의미                                             | 코드 식별자      |
| --------------- | ------------------------------------------------ | ---------------- |
| 검색어          | 사용자가 검색창에 입력한 문자열 원본             | `query`          |
| 정규화된 검색어 | trim + 소문자 변환한 검색어                      | (필터 함수 내부) |
| 검색 중         | 정규화된 검색어가 빈 문자열이 아닌 상태          | —                |
| 검색 결과       | 검색어와 일치하는 노트 목록 (`notes`의 부분집합) | —                |
| 검색창          | 사이드바 상단의 입력 컴포넌트                    | `NoteSearch`     |
| 일치            | `title` 또는 `content`가 정규화된 검색어를 포함  | —                |

## 7. 향후 확장 가능성 (이번 범위 아님)

하이라이트/스니펫, 단어별 AND 매칭, 제목/본문 범위 필터, 서버 검색, URL 쿼리 반영.
